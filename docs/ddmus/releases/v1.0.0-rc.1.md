## The Spotify blocker

The owner's Spotify check on `7606c356` failed: a selected track showed "Buffering…" for more than a minute and never played, while YouTube Music played. This blocked the candidate until it was fixed.

- **Diagnosis.** The failing run's log had no Spotify sync result from start to quit, then "catalog sync did not stop within 5s": Spotify was stuck before the track was chosen. `ensureSession` created the session with a context that had no deadline, and go-librespot puts a deadline on its access-point connection only when the context has one. An access point that accepted the connection and went quiet was therefore waited on forever, with the session lock held, and the track's open queued behind it. The stall is intermittent and was not reproduced: seven starts and nine tracks on the same configuration worked.
- **Cause in ddmus.** Upstream's `deb2f447` bounds session setup at 30 seconds. The port of that commit on 2026-10-03 took its Web API and lyrics timeouts and missed this half. v0.10.0 has the same unbounded wait.
- **Fix** (`3fcf2447`). Session setup has one 30-second budget: the access-point connection and the first Web API token refresh share its context. When it runs out, setup ends with an error that is not a sign-in problem, the half-built session is closed, the lock is released, and the next Spotify action tries again.
- **Tests.** A session creator that waits for its context: `ensureSession` returns the deadline error, releases the lock, and lets a queued caller and a following call through. A stalled token endpoint behind a 30-second client: the refresh ends with the setup's deadline. Negative controls: with either bound removed, the matching tests fail ("did not return within 5s").
- **Review.** Codex, high effort, two rounds. Round one found the access-point hang fixed and raised one MEDIUM finding: the first token refresh ignored the setup deadline, so a stalled token endpoint could hold the lock about a minute longer and end in a sign-in message. Carrying the setup context into that refresh resolved it. Round two: no significant findings.
- **Live.** With the complete fix, on the owner's configuration, the session came up and Spotify tracks played.
- **Accepted limit.** go-librespot's login proof-of-work does not honour cancellation, so an unusually expensive challenge could still outlast the budget. It is the library's, and not worked around here.

## Findings, not fixed in this candidate

None blocks the candidate; each is recorded so the audit after publication starts from them.

1. **The yt-dlp prompt.** With YouTube Music configured and yt-dlp missing, ddmus asks at startup, before anything else, to "Press Enter to install automatically, or Ctrl+C to skip". Ctrl+C does not skip: it quits ddmus. Enter runs `pip install yt-dlp`. Inherited from cliamp.
2. **"sync failed" before anything is set up.** A fresh home with no `~/Music` shows "sync failed · cached" in the header, and a Spotify section without a sign-in shows "Spotify sync failed" until the first sign-in.
3. **Lyrics.** When LRCLIB answers "server busy", ddmus shows "No lyrics found" until `r` retries. A track with no artist tag is never looked up.
4. **A second instance** of ddmus cannot take the MPRIS name; the log says so and playback works.
5. **A token refresh that fails at once** during Spotify session setup (a refused connection, a server error) still ends in the session without a Web API token, whose message mentions signing in again. Only a setup that runs out of time is treated as transient.
